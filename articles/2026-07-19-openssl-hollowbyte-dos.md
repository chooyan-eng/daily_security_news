# OpenSSL「HollowByte」— わずか11バイトの TLS リクエストでサーバーメモリを枯渇させる DoS 脆弱性

- **日付**: 2026-07-19
- **出典**: [BleepingComputer](https://www.bleepingcomputer.com/news/security/hollowbyte-ddos-flaw-bloats-openssl-server-memory-with-11-byte-payload/)
- **トピック**: [OpenSSL HollowByte メモリ枯渇 DoS 脆弱性（2026年）](../topics/openssl-hollowbyte-dos-2026.md)
- **分類**: 新規

## 概要

OpenSSL に、わずか11バイトの悪意ある TLS ペイロードを送るだけでサーバーのメモリを継続的に枯渇させることが可能な脆弱性「HollowByte」が発見された。未認証の攻撃者が TLS ハンドシェイク中に偽装した長さフィールドを送ることで、OpenSSL 側に不当な事前メモリ確保をさせ、glibc のメモリアロケータの挙動と組み合わせることでサーバーの常駐メモリ使用量（RSS）を継続的に増大させ、最終的に OOM（メモリ枯渇）によるサービス停止に追い込むことができる。

## 詳細

### 攻撃手法

未認証の攻撃者は TLS コネクションを開き、後続に大きなメッセージボディが続くと偽装したヘッダーを含む、わずか11バイトの悪意あるペイロードを送信する。OpenSSL の TLS ステートマシンは4バイトのハンドシェイクヘッダーを読み取り、ヘッダー内の3バイトの長さフィールドの申告のみに基づいて `malloc()` による事前メモリ確保（最大131KB）を検証なしに実行してしまう。

### メモリ枯渇のメカニズム

OpenSSL 自体はコネクション切断時にバッファを解放するが、GNU C ライブラリ（glibc）は小〜中規模のメモリ確保分を即座に OS へ返却せず、再利用に備えて保持し続ける。攻撃者がランダム化した申告サイズで大量のコネクションの波状攻撃を仕掛けることで、glibc アロケータが解放済みチャンクを再利用できない状態に追い込まれ、サーバーの RSS（常駐メモリセットサイズ）が継続的に増加し続ける。

### 検証結果

Okta のセキュリティチームによる NGINX を用いた検証では、1GB メモリのサーバーが 547MB のメモリをフラグメント状態で凍結された末に OOM Killer によって強制終了された。16GB メモリのサーバーでは、コネクション数の上限に達することなくシステムメモリの25%が占有される状態に陥った。

### 修正状況

本脆弱性は2026年6月に OpenSSL 側で修正されたが、当初は CVE 番号の割り当て・セキュリティアドバイザリ・変更履歴（changelog）への明記が一切なく、修正の存在自体が広く認知されていなかった。現在は OpenSSL 4.0.1 で修正済みであり、3.6.3・3.5.7・3.4.6・3.0.21 にもバックポートされている。

### 推奨対策

- 使用中の OpenSSL / TLS ライブラリを最新のバックポート版（3.6.3 / 3.5.7 / 3.4.6 / 3.0.21 以降、または 4.0.1 以降）に更新する
- リバースプロキシ・ロードバランサー層でのコネクションレート制限や異常なハンドシェイクパターンの監視を強化する
- メモリ使用量の急激な増加を検知するアラートを設定し、OOM 発生前に対応できる体制を整える
